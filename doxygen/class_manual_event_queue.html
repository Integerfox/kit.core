Detailed Description

This class is an Event Queue (Kit::EventQueue::Server) that is NOT run by a thread.

Instead, the unit test runs it - on the test's own thread - by calling runUntilIdle(). The test therefore controls exactly when the code that executes in the Event Queue's context (ITC requests, Model Point change notifications, event flag handlers, software timer callbacks) runs - and, for software timers, how much time has passed (see advanceTime()). This makes tests deterministic: once runUntilIdle() returns true, the queue's servers have processed everything they are going to process, i.e. 'nothing happened' checks need no sleeps, and 'something happened' checks need no polling/timeouts.

How to use:

  1. Construct a ManualEventQueue instead of a Kit::EventQueue::Server, and pass it to the object(s) under test as their Event Queue. Do NOT create a thread for it.
  2. Open/close servers with requestOpen()/requestClose() - NOT with the server's synchronous open()/close() methods (see the 'Limitations' below). Other ITC requests are sent with postAndRun().
  3. After every stimulus (e.g. writing a Model Point, adding an entry to a RingBufferMP), call runUntilIdle() and then check the results. Wrap the call in REQUIRE() - a false return value means the server never became idle (i.e. it is busy-looping).

Example (a server that implements Kit::Itc::OpenCloseSync, and processes Model Point change notifications):

#include "Kit/_support/testing/ManualEventQueue.h"
TEST_CASE( "MyServer" )
{
ManualEventQueue eventQueue; // No thread!
MyServer uut( eventQueue, mp_input_ );
REQUIRE( eventQueue.requestOpen( uut ) ); // Instead of uut.open()
mp_input_.write( 42 ); // Stimulus...
REQUIRE( eventQueue.runUntilIdle() ); // ...let the server react...
REQUIRE( uut.m_count == 1 ); // ...and check the exact result
mp_input_.write( 42 ); // No change -->no notification
REQUIRE( eventQueue.runUntilIdle() );
REQUIRE( uut.m_count == 1 ); // Deterministic 'nothing happened' check
REQUIRE( eventQueue.requestClose( uut ) ); // Instead of uut.close()
}

Limitations:

  • Synchronous ITC calls (e.g. Kit::Itc::OpenCloseSync::open()/close(), or any other xxxSync API) block until a server thread processes the message - there is none, i.e. the call never returns. Use requestOpen(), requestClose(), or postAndRun() instead.
  • Messages are sent with a 'null' return handler, i.e. the server's returnToSender() does nothing. Read the results from the payload after the call.
  • Software timers (Kit::System::Timer and friends that use the queue as their Kit::System::ITimingSource) run on the queue's own virtual clock, which starts at zero and ONLY advances with advanceTime(). Code that reads the system clock directly (e.g. Kit::System::ElapsedTime) still sees real time.
  • The queue must only be run by ONE thread (the test thread). Code under test that creates its own threads is not made deterministic.

NOTE: The class is intended for unit tests only.

◆ advanceTime()

bool ManualEventQueue::advanceTime ( uint32_t milliseconds)
inlinenoexcept

Advances the queue's virtual clock by 'milliseconds', one millisecond at a time.

For each millisecond, the expired software timers' callbacks are called, and then the queue is run until idle (i.e. the work that the callbacks generate is processed before the clock advances again - the same order as a running Event Queue). A periodic timer, i.e. one that restarts itself from its expired callback, therefore expires once per period. Pending work is processed before the clock is advanced. Returns false (immediately) if the queue does not become idle.

◆ runUntilIdle()

bool ManualEventQueue::runUntilIdle ( unsigned maxIterations = OPTION_KIT_TESTING_MANUAL_EVENT_QUEUE_MAX_ITERATIONS,
unsigned * retIterations = nullptr )
inlinenoexcept

Processes the signaled event flags, pending ITC messages, and change notifications until there is no pending work, or 'maxIterations' iterations have been performed.

Each iteration notifies the event flag handlers first (the same order as a running Event Queue). Returns true when the queue is idle, i.e. false means the server(s) never stopped generating work (e.g. busy-looping). The number of iterations performed is optionally returned via 'retIterations'.
